# Кампания устойчивости HICS

[Краткий статус и открытые задачи](RELIABILITY_STATUS.md).

Цель — полная проверка установки и функций на CachyOS, провокация отказов,
исправление находок, анализ ресурсов и понятная диагностика. Этот документ —
журнал доказательств и оставшейся работы, а не заявление «всё проверено».

## Испытательное окружение

- QEMU/KVM, 2 vCPU, 4096 MiB RAM, виртуальный диск 60 GiB (qcow2, thin).
- Нет проброса физических дисков, общих каталогов или изменения сети хоста.
  Сеть user-mode; SSH опубликован только на 127.0.0.1:22280.
- QMP и serial — Unix-сокеты в приватном каталоге лаборатории.
- Официальный ISO CachyOS Desktop 260809. SHA256:
  `959f6577f45e25ee9fd8c220fd221b08e4ea79412c7315c0f922dd6d86d5e33c`.
  Проверена подпись ключом `882DCFE48E2051D48E2562ABF3B607488DB35A47`
  из установленного cachyos-keyring. Его armored public-key file сначала
  преобразован через gpg --dearmor, затем выполнен gpgv.
- Источники: [ISO и проверка](https://wiki.cachyos.org/cachyos_basic/download/),
  [зеркало ISO](https://build.cachyos.org/ISO/desktop/260809/),
  [systemd debug console](https://www.freedesktop.org/software/systemd/man/latest/systemd-debug-generator.html).
- Базовая ОС установлена guarded pacstrap из официального live-окружения.
  Это не тест Calamares. Подтверждены ID=cachyos, ядро linux-cachyos 7.2.7-1,
  CachyOS settings, UEFI/GRUB, Btrfs @/@home и загрузка с диска без ISO.
  На базовом старте systemctl --failed не содержит юнитов.
- Базовый диск сохранён отдельно; эксперименты идут в overlay. Root-доступ
  лаборатории — по отдельному SSH-ключу. Ключи, диски, пароли и сырые логи
  не добавляются в Git. Debug-shell включается только для установочного
  live ISO; установленная ОС запускается без него.

## Воспроизведение

Скрипты находятся в tests/:

- `run_stability.py --out PRIVATE_DIRECTORY` — каждый test_*.py отдельно,
  с приватными HOME/XDG, недоступными настоящими D-Bus-шинами, offscreen Qt,
  таймаутом и отдельным логом. Manifest содержит исходную ревизию, dirty-state,
  результаты, пропуски и SHA256 изменённых исходников. Первый baseline был
  снят до добавления fingerprint-списка; это ограничение его доказательств.
- `vm_cachyos.py start --lab PRIVATE_DIRECTORY` — boot официального ISO.
  ISO, SHA256, извлечённые kernel/initrd должны находиться в каталоге lab.
- `vm_cachyos.py start --installed --lab PRIVATE_DIRECTORY` — boot диска;
  `status` использует настоящий QMP, `stop` посылает QMP quit.
- `vm_bootstrap_cachyos.sh --disposable-cachyos-vm` выполняется **внутри ВМ**.
  Guard проверяет QEMU, live ISO, пустой writable vda размером ровно 60 GiB.
  Повторный запуск на размеченном диске запрещён. Установленные настройки
  рассчитаны на тестовый стенд, не на развёртывание пользовательского ПК.

Перед snapshot/reset остановить гостевую ОС, проверить освобождение qcow2 и
не перезапускать ВМ только из-за истечения времени наблюдения. Её живость
подтверждается QMP и состоянием процесса. Команды разрушения ОС, OOM, обрывов
установки и kernel panic разрешены исключительно в disposable guest.

## Результаты первого базового прогона

63 модуля, 313 тестов, 5 пропусков, два упавших модуля. Логи сохраняются
раздельно; baseline не переписывается последующими зелёными результатами.
Пропуски: два теста application scopes требуют user systemd, один broker
runtime требует user systemd, два network QML требуют Wayland. Они остаются
незакрытыми до отдельного подходящего прогона.

После baseline выполнены отдельные прогоны с нужными условиями:
application scopes — 2/2 на реальном user systemd (только временные fixture
units); broker runtime — 8/8, включая зависание и рестарт только его временного
юнита; network QML — 2/2 с Wayland и приватным NetworkManager fixture.
Пропусков в этих трёх прогонах нет. Это закрывает перечисленные предпосылки

## Первая установка пакета

Кандидат hic-shell 1.1.1-79 установлен публичным install.sh --package от обычного
hics-test пользователя без GUI и без его user bus. Для автоматического стенда
выдано guest-only sudo-разрешение на pacman; это не настройка хоста/продукта.

Проверено: dry-run, разрешение/загрузка зависимостей, установка, включение
hics-system/hics-memory и четырёх пользовательских юнитов, активность двух
системных служб, отсутствие failed units. Это **не** доказательство рабочего
графического сеанса: GUI/логин/каждая функция ещё требуют испытаний.

## Дополнение: безопасный первый вход и восстановление

Проверка текущего кода подтверждает наличие отдельного минимального recovery UI,
защиты от повторных падений, рабочей стартовой точки и пробного отката через
существующий configuration guard. Это реализованные механизмы, а не новые
дублирующие службы. Приоритет дальнейшей разработки — проверка их полного
сценария в гостевом графическом сеансе, затем остальные пункты матрицы выше.

**INSTALL-002:** пакет не предоставлял отдельный сеанс HICS и требовал ручного
копирования конфигурации. Добавлены hics-start и запись wayland-sessions;
подготовка сохраняет существующие файлы, публикует новые атомарно и использует
отдельный каталог для новой сессии. Повреждённая чужая конфигурация не мешает
подготовке. Проверяются конкурентный запуск и путь установки с пробелами.
Реальный запуск ярлыка проверен Gio, а не только разбор строки Exec.

**RECOVERY-001:** чтение журнала аварий могло заблокироваться на FIFO вместо
обычного файла. Теперь используется неблокирующее открытие без следования
symlink, проверка fstat и ограниченное чтение. Повреждённая запись заменяется
приватным журналом; внешний файл по symlink не изменяется. Рабочая точка
также отвергает NaN/Infinity внутри сохранённых секций. Добавлены fault-case
тесты. Создание snapshot также проверяет размер до чтения и ограничивает
само чтение секции одним MiB, включая случай роста файла. Новых таймеров, процессов в простое или постоянных служб нет.

**TEST-002:** прямой запуск GTK fixture наследовал реальную политику хинтинга
пользователя. Исходное состояние теста теперь явно задано; чтение сохранённой
политики отдельно проверяется в приватном XDG-каталоге.

Установка этих изменений на рабочий хост в рамках этого дополнения не выполнена.


Проверки этого этапа:

| Механизм | Реальное состояние | Проверка |

## Графический сеанс CachyOS: проверка в гостевой системе

ВМ действительно прошла первый графический вход через greetd/PAM, затем
logout и обычный вход с паролем. Пароль синтетический, только для гостя;
он не публикуется. greetd — инфраструктура стенда, а не навязанная зависимость
или изменение менеджера входа пользователя. Установленный пакет последовательно
обновлялся до 1.1.1-84; последующий fresh replay приведён ниже.

Через настоящую панель и меню приложений виртуальной мышью/клавиатурой открыт
Kitty. Его cgroup — отдельный `app.slice/hics-app-*.scope`. Два SIGKILL процесса
HICS дали нормальный перезапуск после первого падения и safe shell после второго.
Процесс и scope приложения сохранились. После исправления recovery UI выполнены
реальные клики: просмотр/подтверждение восстановления → обычная оболочка →
подтверждение профиля в 30-секундном окне. Приложение пережило и этот переход,
и обновление пакета. Повтор на установленном 83 выполнен скриптом
`tests/vm_recovery_cycle.py`; итог сохраняется в `crash-cycle83.json` стенда.
Скрипт проверяет QEMU/KVM и гостевой hostname, отказывается перезаписывать
предыдущие доказательства, оставляет safe mode для визуального осмотра.

Новые находки:

| INSTALL-003 | В чистой CachyOS нет UPower/RealtimeKit, хотя интерфейс и PipeWire их используют | Явные зависимости upower/rtkit и bluez. После установки UPower доступен через system D-Bus. power-profiles-daemon остаётся опциональным: нельзя безусловно подменять существующий менеджер питания |
| INSTALL-004 | Прямой Hyprland выдаёт предупреждение о запуске без штатного watchdog | hics-start использует `start-hyprland -- --config …`; реальный повторный PAM-вход показывает launcher и дочерний Hyprland с watchdog fd |

(`src/launch/launch.cpp`, `src/core/qmlglobal.hpp`). AppId — штатная pragma;
путь shellDir — путь корня, а не URL.

Измерение простоя кандидата 82: 10 секунд, один монитор, открытый Kitty,
после затухания интерфейса; HICS ≈0.2% одного ядра, Hyprland ≈0.1%, Kitty 0%.
RSS HICS ≈673 MiB. Это **один замер** в virtio-vga 2D с программным рендерингом,
не сравнение ускорения и не доказательство отсутствия утечки. ВМ закономерно
имеет EGL/SHM/отсутствующий аппаратный видеодекодер; выводы о реальном GPU,
VRAM и холодном старте на физическом ПК по этому измерению не делаются.

Полная кампания остаётся открытой: fresh replay с исправленным resolver,
холодная загрузка, все функции/страницы/виджеты, длительная память и аппаратные
интеграции ещё не подтверждены полностью. На хосте сохраняется пакет 1.1.1-78;
его нативные плагины не выгружались и не перезагружались.


### Повтор чистой установки кандидата 84

После штатного выключения подтверждены завершение процесса QEMU и освобождение

### STAB-003: ограничение ответов системных команд и отказы портала

Fault-case перед исправлением: фиктивный pactl выводил 32 MiB stderr,
DesktopIntegration передавал все 33 554 432 символа в error/UI. Большой stdout

4096 байт stderr. Общий finish защищён от повторного вызова; FailedToStart,
нормальное завершение, timeout и overflow освобождают pending. Таймаут отличим
от прочих ошибок. Для тихого capture-monitor отказ очищает данные и устанавливает
unavailable. В journal пишется компонент и категория отказа, без argv и сырого
stderr. Добавлены русские переводы новых объяснений; общий FeatureError сохраняет
существующее оформление. Это лимиты payload, не измерение полного RSS процесса.

tests/test_desktop_integration_native.py расширен до 23 случаев: stdout/stderr
flood, тихий capture flood, зависание команды до штатного 15-секундного timeout,
ошибка exec, portal malformed/hang/late, уничтожение backend до позднего ответа,
смерть D-Bus owner и повтор к новому процессу-владельцу. Последний сценарий
использует один живой экземпляр C++ backend на обе фазы. Для portal hang/late
проверяется возврат busy=false и отсутствие публикации запоздавших capabilities.

разрешения/передача PipeWire stream внешнему приложению.

Системная и session D-Bus шины, аудио endpoints и tools теперь изолированы
явно. Qt 6.12 направлял logging в journal, поэтому прежнее ожидание warning
в захваченном stderr было неверным. Fixture использует QT_FORCE_STDERR_LOGGING,
сохраняя проверку контекстной диагностики без персональных данных.
Источник API: [QProcess](https://doc.qt.io/qt-6/qprocess.html),

### CONFIG-WATCH-004: отказ записи во время автоматического отката

### RUNNER-CLEANUP: отказ маркера расширений и stop во время перехода

Намеренный OSError ENOSPC в extension_recovery.finish воспроизвёл исключение
из finally run_session: закрытие compositor socket, восстановление signal
handlers/wakeup_fd и закрытие pipe не выполнялись. Unit до правки упал на
finish_extensions(result). Очистка сигналов/FD теперь в отдельном finally;
ошибки маркеров и ожидаемые ошибки workspace cleanup диагностируются и не
маскируют успешный выход UI. Реальная ошибка сохранения выбранного режима
по-прежнему возвращается как ошибка, без ложного transition success.

Регрессия запускает настоящий runner и дочерний процесс, инъецирует отказ
extension marker и отдельно commit режима; проверяет прежние SIGTERM/INT/CHLD
handlers, wakeup_fd и точное множество /proc/self/fd до/после. Неудачный commit
не записывает requested=true. Это fault injection, не настоящий полный диск ВМ.

Дополнительно обработчик сигнала сохраняет termination_requested в памяти:
SIGTERM/INT имеет приоритет над exit75/76. Раньше wakeup pipe читался только
в selector, поэтому сигнал во время обработки уже завершившегося UI мог
потеряться между выходом из цикла и повторным run_session. Тест посылает
настоящий SIGTERM себе внутри commit и ожидает return0 вместо повторного
запуска. В POSIX handler нет Qt API/ожиданий/файловых операций.

29 recovery-тестов (расширены сценарии внутри реального runner fixture),
2 session restart-теста, реальный IPC transition и recovery QML+guard прошли.
В установленном пакете97 этих последних cleanup/signal исправлений ещё нет.
Сценарии одновременных настоящих lock/transition в ВМ и отказа реального
хранилища при commit остаются открытыми.

### STARTUP-CANCEL: прекращение подготовки при stop

prepare_session ожидал отдельные preflight helpers до20/35s без реакции на
termination_requested, тогда как hic-session.service TimeoutStopSec=10.
Принудительное завершение runner в этом интервале могло оставить его отдельные
helper process groups. Подготовка теперь принимает cancellation predicate;
проверяет его до spawn/theme/каждого ожидания и ограничивает порцию wait250ms.
При отмене finally убивает и reap незавершённых помощников, QML не запускается.
Успешный wait возвращается сразу: искусственной задержки startup не добавлено.
Синхронное восстановление GTK остаётся отдельной ограниченной операцией;
полная отмена произвольного файлового I/O этим не обеспечивается.

Проверены5 startup cases: порядок параллельной подготовки, timeout/reap,
отмена с подставными детьми, отмена трёх настоящих Python sleep60 процессов,
неизменность inode/mtime темы. Реальный cancel-test завершился в пределах3s
(весь модуль~0.51s), все3 ребёнка reap. Fake PID fixtures теперь всегда
подменяют killpg, чтобы не адресовать существующие процессы машины теста.
29 recovery и2 session-restart tests также прошли. Изменение после пакета97;
установленная ВМ ещё не подтверждает этот cancellation path.

### STARTUP-DESCENDANTS: потомок переживает завершившегося помощника

Новый реальный тест запускает по помощнику на preflight job; каждый создаёт
sleep60 в своей группе и сам завершается успешно. До исправления тест упал:
все3 потомка продолжали жить, потому что cleanup проверял только leader.poll().

Ожидание заменено на pidfd readiness + waitid(WEXITED|WNOWAIT). Статус лидера
наблюдается без reap; до освобождения зарезервированного PID/PGID cleanup
останавливает группу и только затем вызывает Popen.wait. Нельзя просто вызвать
killpg после старого wait: между reap и kill номер мог быть переиспользован.
pidfd poll возвращается сразу при готовности, нет добавленной задержки250ms
успешному startup; poll также не имеет FD_SETSIZE ограничения select.select.
Открытый pidfd всегда закрывается в finally. API доступен в целевом Linux,
Python>=3.11; зависимостей и resident сервисов не добавлено.

Первичная документация:
https://docs.python.org/3/library/os.html#os.waitid
https://docs.python.org/3/library/os.html#os.WNOWAIT
https://docs.python.org/3/library/os.html#os.pidfd_open

Тест усилен: каждый helper создаёт также detached sleep60 с новой сессией.
После cleanup 3 managed descendants не работают, 3 detached живы; fixture
после проверки завершает и их. Это проверяет границу очистки: собственные
configuration/display guards с start_new_session не должны быть убиты.
Сама проверка /proc/stat исправлена для ESRCH при исчезновении inode во время
read, не только ENOENT. Все6 startup и29 recovery tests проходят;2 session
restart tests прошли после основной правки. Установленный пакет97 пока старый.
