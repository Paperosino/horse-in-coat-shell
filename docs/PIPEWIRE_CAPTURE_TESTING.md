# Проверка захвата экрана и индикатора приватности

Состояние кампании на 28 октября 2026: это приёмка конкретных сценариев,
а не подтверждение исправности всех порталов, камер и GPU. Установленный
на рабочем компьютере пакет116 остаётся прежним до приёмки нового пакета.

## Событийный монитор

`DesktopIntegrationMonitor.qml` использует существующее подключение
Quickshell к PipeWire. Привязаны только `Stream/Input/Video`, а не весь граф.
Закреплённая исходная версия QS0.3.2 дополнена типами видео-потоков и
сигналом состояния узла. Состояния берутся из `pw_node_info` при
`PW_NODE_CHANGE_MASK_STATE`, а не выводятся из таймера или наличия процесса.
См. [публичный Node API PipeWire](https://docs.pipewire.org/group__pw__node.html).

Снимок передаётся в C++ после объединения событий текущего оборота event loop.
Сохраняются имя приложения, serial, id, состояние и явная роль Screen/ScreenCapture.
Повтор одинакового снимка не вызывает лишнего уведомления. Разрыв соединения
очищает список и снимает доступность монитора. Старый ответ `pw-dump` не может
перезаписать новый снимок. Для отдельных клиентов C++ без QML-монитора
сохранён резервный путь. В обычной оболочке он отключён до первого опроса.
Таймер операций со съёмными накопителями этим изменением не удалён.

Это индикатор, а не механизм запрета доступа к устройствам. Если приложение
не сообщает роль захвата экрана, поток не выдаётся за доказанный ScreenCast.
Состояния suspended/idle/running сохранены для подробного интерфейса.

## Настоящий ScreenCast в CachyOS VM

`tests/integration_screencast_frames.py` запускается от тестового UID1000
только внутри disposable QEMU/KVM с hostname hics-test и разблокированным
сеансом. Он использует настоящий frontend портала, диалог выбора источника
и выданный `OpenPipeWireRemote` файловый дескриптор. Постоянное разрешение
не запрашивается, кадры и restore tokens не записываются.

Нативные инструменты собираются отдельно от релизной оболочки:

```sh
cmake -S tests/fixtures/pipewire-probes -B /tmp/hics-pw-probes -GNinja
cmake --build /tmp/hics-pw-probes -j2
```

`portal-pipewire-frames-*` требует 12 меняющихся кадров, возвращает каждый
полученный буфер, ограничивает размеры и время ожидания. Использует
`pipewire-serial` / `PW_KEY_TARGET_OBJECT`, когда портал предоставляет serial;
node-id оставлен для старого API. Это соответствует
[ScreenCast API v6](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.ScreenCast.html).
После Session.Close контроллер проверяет исчезновение узла с тем же serial.

Для наблюдения используется `tests/fixtures/capture-monitor.qml` с копией
текущих QML/native модулей и нового QS. Его 120-секундный ограничитель —
только испытательная обвязка. Пути импорта обязательно включают частный Qt
из пакета, а не одноимённые системные QML-модули другой версии.

Первый реальный сценарий нового монитора: источник1280×800,12 кадров,
11 отличающихся от первого, consumer exit0, Session.Close успешен, узел
источника исчез. Зафиксированы события клиента suspended → running → удалён,
продолжительность существования клиентского узла около0,74с. Это конкретное
наблюдение, не универсальная оценка задержки. Основной UI594 и backend655
в этой ВМ сохранили процессы. Предыдущие проверки отдельно подтвердили
захват окна640×360 и отказ от выбора источника.

`vm_guest_pointer.py` перед нажатием проверяет реальные координаты курсора
композитора. QEMU может не отправить повтор одинаковых абсолютных осей после
warp курсора, поэтому нужен уход и возврат. Несовпадение координат, lock,
другая геометрия или hostname запрещают нажатие. Три mock-теста и реальное
нажатие прошли. Ошибка этого стенда не выдаётся за ошибку ввода оболочки.

## Открытые находки и честные границы

В PipeWire1.6.10 минимальный отдельный C-процесс с созданием/уничтожением
контекста воспроизводит LSan:3671байт/34allocation за один контекст,
36710байт/340allocation за десять. Маппинг кадров стека указывает на
libdbus и libpipewire-module-rt. В raw consumer также получено3677байт/34.
Это красный baseline, его результат не скрыт и не считается исправлением.

Отдельный контроль `owned-dbus` заранее инициализирует DBus в приложении
и держит связанный libdbus загруженным. Десять контекстов и реальный захват
экрана в этом контроле проходят ASan/LSan. Он моделирует уже использующий
DBus процесс; результат не доказывает чистоту raw пути выгрузки модуля.
Production не получает `dbus_shutdown`, LD_PRELOAD, sanitizer suppressions
или отключение аппаратных/RT функций ради зелёного отчёта.

В xdg-desktop-portal-hyprland1.4.1 при таймауте выбора источника закрытие
Request/Session не убрало диалог picker. Собственное тестовое окно закрыто
обычным действием WM, backend не перезапускался. Escape также не закрыл
этот QMainWindow. Причина и полноценное исправление отмены внешнего picker
остаются отдельной задачей; нормальный отказ через закрытие окна проверен.


## Восстановление backend после отказа PipeWire

Подтверждён отдельный сбой xdg-desktop-portal-hyprland1.4.1: после restart
PipeWire его процесс655 остался жив, но больше не был клиентом нового сервера.
SelectSources работал, Start не завершался; повторный вход не требуется для
воспроизведения. Запрос завершился response2 при восстановлении backend.

Кандидат117 устанавливает drop-in `50-hics-pipewire-lifetime.conf`:
`BindsTo=pipewire.service`, `After=pipewire.service`. По
[документации systemd](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html#BindsTo=)
эта связь распространяет остановку/перезапуск сервера и не позволяет backend
оставаться активным с неработающей зависимостью. Она не добавляет таймер,
наблюдающий процесс или периодические рестарты. Уже идущая запись при отказе
сервера завершается; новое разрешение запрашивается обычным порталом.

В disposable ВМ проверены два случая:

- Обычный restart PipeWire заменил backend655→5365; последующий захват окна
  вернул12 кадров640×360,10 меняющихся, consumer exit0 и чистый ASan/LSan.
- SIGKILL главного процесса PipeWire остановил backend5365. PipeWire вернулся
  по своей штатной Restart=on-failure политике. Следующий настоящий portal
  запрос сам активировал backend5662; захват экрана1280×800 вернул12 кадров,
  11 меняющихся, consumer exit0, Session.Close и удаление serial успешны.

Окончательный QS binary SHA256:
`eea11eb0ecb86c7cd34318ec65956de392e1736d172090585aa33c3d010c530e`.
Монитор пережил потерю сервера, сообщил available=false→true и получил
новый захват. Отдельный marker, доступный только процессу наблюдателя,
не обнаружил запусков pw-dump. Контроллер вправе вызывать pw-dump для проверки
удаления узла; его окружение отделено от marker. Первоначальный общий marker
был загрязнён этим диагностическим вызовом и не считается доказательством.
UI594, тестовое окно2891 и NRestarts=0 основной сессии сохранились.

Полный изолированный прогон:80 модулей,485 тестов,0fail/timeout,6 явных
пропусков окружения. Дополнительно4 native snapshot сценария ASan/UBSan/LSan,
17 runtime/allocator тестов и21 packaging/installer тест проходят. Финальное
изменение установки drop-in проверяется также отдельной приёмкой пакета;
этот отчёт ещё не объявляет кандидат117 установленным на хосте.
